## 一、Transformer / GPT 结构

### 1. GPT-2 一个 Block 的结构是什么？
Pre-LN 结构，两个子层，每个子层都是"先 LayerNorm → 再计算 → 加回残差"：
```
x = x + attn(ln_1(x))
x = x + mlp(ln_2(x))
```
GPT-2 124M 有 12 个这样的 Block，前面是词嵌入 + 位置嵌入，后面是 ln_f + lm_head。

**项目里：** `miniserve/model.py` 的 `Block`、`GPT2`。

### 2. Pre-LN 和 Post-LN 有什么区别？为什么 GPT-2 用 Pre-LN？
- Post-LN（2017 年原始 Transformer）：`x = ln(x + attn(x))`，先加残差再归一化
- Pre-LN（GPT-2 及之后大多数大模型）：`x = x + attn(ln(x))`，先归一化再进子层

Pre-LN 训练更稳定：残差这条路上的 x 不经过任何处理，从输入一路直通到输出，层数很深时梯度也不容易出问题。

### 3. 残差连接的作用？
子层算出来的不是"全新的 x"，而是对 x 的**修正量**，每层在原来的基础上加一点信息。好处是信息和梯度都能沿残差路径直接传递，深层网络更容易训练。

### 4. 为什么每个 Block 有两个 LayerNorm（ln_1、ln_2）？
1. 两次的输入不一样：ln_2 处理的是已经加上 attention 输出之后的 x
2. LayerNorm 的 weight、bias 是可学习的，attention 和 MLP 需要的输入分布不同，所以各学一套参数

整个 GPT-2 一共 12 × 2 + 1（ln_f）= 25 个 LayerNorm。

### 5. LayerNorm 做了什么？
对**每个 token 的向量单独**归一化：先减均值、除以标准差，变成均值 0、方差 1；再乘以 weight、加上 bias（可学习）。作用是让送进下一层的数值大小稳定。

（后续 M4 的 RMSNorm：省掉减均值这一步，也没有 bias。）

### 6. Self-Attention 是怎么计算的？
```
qkv = x @ W_qkv + b        (B, T, 3C)，一次矩阵乘同时算出 q、k、v
拆成 q, k, v               各 (B, T, C)
拆头                        各 (B, nh, T, hs)
scores = q @ kᵀ / √hs       (B, nh, T, T)
因果 mask + softmax          (B, nh, T, T)
y = att @ v                 (B, nh, T, hs)
合并头                       (B, T, C)
输出投影 c_proj              (B, T, C)
```
**项目里：** `CausalSelfAttention.forward`；热身练习 `exercises/tensor_exercises.py` 第 1~5 题。

### 7. 为什么要除以 √d（每个头的维度）？
q·k 是 d 个数相乘再相加，d 越大，点积的数值（方差）越大。数值太大时 softmax 会变得非常"尖"，几乎全部权重集中在一个位置，梯度也会变得很小。除以 √d 把数值拉回正常范围。

### 8. 多头注意力是怎么拆头的？为什么不能直接 view 成 (B, nh, T, hs)？
每个 token 的 C 维在内存里是连续的：`[头0的 hs 维 | 头1的 hs 维 | ...]`。`view` 不移动数据，只按内存顺序重新分组。直接 view 成 (B, nh, T, hs)，会把连续的 T×hs 个数分给一个头，结果头 0 拿到的是 token 0 的完整向量，而不是每个 token 的前 hs 维。

正确做法：先 `view(B, T, nh, hs)` 按内存顺序切，再 `transpose(1, 2)` 交换维度。合并头是逆操作：`transpose(1, 2).contiguous().view(B, T, C)`。

### 9. 因果 mask 的作用？为什么填 -inf 而不是 0？
GPT 从左往右生成，第 i 个 token 只能看自己和前面的 token（下三角）。

softmax 先算 e^x：e^(-inf) = 0，被遮住的位置权重严格为 0，其余位置的权重之和仍是 1。如果填 0，e^0 = 1，被遮住的位置还会分到权重，等于"看到了未来"。

### 10. Q、K、V 为什么是"一个线性层乘出来再切成三段"？
`nn.Linear` 只负责矩阵乘法；"前 C 维是 q、中间是 k、最后是 v"是 forward 代码规定的切分方式；它们之所以有意义，是因为**训练**时就按这个方式切，权重学会了在对应位置产生适合当 q / k / v 的向量。三者对上，算出来的才是真正的 q、k、v。

### 11. MLP（FFN）的结构？为什么要放大 4 倍？为什么需要激活函数？
`c_fc (768→3072) → GELU → c_proj (3072→768)`。
- 放大到更高维度，模型有更多空间表达复杂特征；4 倍是 GPT-2 的设计选择
- 没有激活函数的话，两个线性层相乘仍然是一个线性层，叠多少层都等价于一层
- GPT-2 用的是 tanh 近似版 GELU（`approximate="tanh"`），用精确版会和官方权重有约 1e-4 的误差

MLP 的参数量比 attention 还多（约 470 万对 236 万 / 层）。

### 12. Attention 和 MLP 的分工？
- Attention：token **之间**交流信息（第 i 个 token 会看前面所有 token）
- MLP：对**每个 token 单独**加工，token 之间没有交互

### 13. GPT-2 的位置编码是什么？
可学习的绝对位置嵌入 `wpe`，一张 (1024, 768) 的表，按位置编号 0, 1, 2… 取行，和词嵌入相加。1024 也就是模型能处理的最大长度（block_size）。

（后续 M4 的 Qwen 用的是 RoPE 旋转位置编码。）

### 14. 什么是 weight tying？
`lm_head` 和词嵌入 `wte` **共享同一份权重** (50257, 768)：输入时把词变成向量，输出时用同一张表给每个词打分。省掉了约 3860 万参数。

**项目里：** `self.lm_head.weight = self.wte.weight`；检查脚本验证了参数量正好是 124,439,808。

### 15. logits 是什么？自回归生成 / 贪心解码怎么做？
`lm_head` 输出 (B, T, vocab_size)，是每个位置对词表里每个词的打分；最后一个位置的打分就是对"下一个词"的预测。

自回归生成：每次预测 1 个词，接到序列末尾，再预测下一个。贪心解码：每次都选分数最高的词（`argmax`），结果是确定的。

**项目里：** `generate`，与 HF 的 `generate(do_sample=False)` 逐 token 一致。

## 二、推理优化

### 16. KV Cache 的原理？
自回归生成时，旧 token 的 k、v 在每一步都一样，不缓存就会被反复重算。KV Cache 把每层算过的 k、v 存起来，之后每一步只需要：
1. 只算**新 token** 的 q、k、v
2. 新的 k、v 拼到缓存后面
3. 新 token 的 q 和缓存里**全部**的 k、v 做 attention

流程分两阶段：**prefill**（整个 prompt 一次送进去，填好缓存）+ **decode**（之后每步只送 1 个新 token）。

**项目里：** `LayerKVCache`、`generate_cached`；位置编号要从已缓存的长度 `past` 接着往后数；有缓存时 mask 要变成 (T, L)，`diagonal=L-T`。

### 17. 为什么只缓存 K 和 V，不缓存 Q？其他层的结果要不要缓存？
- 每一步只需要算新 token 的输出，只用到新 token 的 q；旧 token 的 q 已经用完了
- k、v 会被之后**每一个**新 token 反复使用，所以值得缓存
- LayerNorm、MLP 是每个 token 各算各的，新 token 的计算用不到旧 token 的结果，不用缓存
- **旧 token 唯一会被再次用到的地方，就是它们在每一层的 k 和 v**，这也是"KV Cache"名字的由来

### 18. KV Cache 能提速多少？什么时候提速明显？
序列越长提速越明显。**项目实测（RTX 3060 Laptop，float32，batch=1，prompt 16）：**

| 新 token 数 | 无缓存 | 有缓存 | 提速 | 有缓存每 token |
|---|---|---|---|---|
| 50 | 0.42 s | 0.39 s | 1.1x | 7.7 ms |
| 200 | 1.85 s | 1.42 s | 1.3x | 7.1 ms |
| 500 | 8.40 s | 3.50 s | 2.4x | 7.0 ms |
| 1000 | 35.04 s | 7.26 s | 4.8x | 7.3 ms |

短序列几乎不提速：无缓存时也处在 GPU 的"平坦区"（见第 20 题）。

### 19. KV Cache 占多少显存？怎么算？
```
每 token 的 KV Cache = 2（k 和 v） × 层数 × KV 头数 × 每头维度 × 每个数的字节数
```
- GPT-2（12 层，12 头 × 64 维 = 768，float32）：2 × 12 × 768 × 4 = **72 KB / token**，1024 token ≈ 72 MB
- Qwen2.5-7B（28 层，GQA：KV 只有 4 头 × 128 维 = 512，fp16）：2 × 28 × 512 × 2 = **56 KB / token**，32K token ≈ 1.75 GB

易错点：普通多头注意力里"头数 × 每头维度"已经等于隐藏维度，不要再乘一次头数；GQA 模型要用 KV 的头数，不是隐藏维度。

真实服务中 KV Cache 常常比权重还占显存（Qwen2.5-7B 权重 fp16 约 15 GB，9 个 32K 请求的 KV Cache 就超过它），**能同时服务多少请求主要由 KV Cache 决定**。

### 20. 为什么 decode 阶段是 memory-bound？prefill 呢？
**算术强度** = 每从显存读 1 字节数据能做多少次计算。

- decode：每步只处理 1 个 token，计算量很小，但仍要把**全部权重**从显存读一遍，GPU 大部分时间在搬数据 → **memory-bound**
- prefill：一次处理整个 prompt，读一遍权重能给很多 token 用 → 算术强度高 → 更接近 **compute-bound**

**项目实测（一次前向耗时 vs 序列长度）：** 长度 16 / 64 / 128 都是约 8 ms，几乎不变（计算量涨了 8 倍，时间没变）；之后才开始增长，1024 时约 75 ms。平坦区的耗时与 T 无关。

**修正（M2 第 4 步用 profiler 实测）：** batch=1 时 decode 一轮墙钟约 8.2 ms，GPU 真正在执行 kernel 的只有约 2.3 ms（这部分是读约 500 MB 权重，确实是 memory-bound），其余约 70% 是 CPU 发射几百个小 kernel 的开销。所以 GPT-2 small 这种小模型在 PyTorch eager 模式下，端到端其实是 **launch-bound（CPU-bound）**；模型越大、每个 kernel 越重，才越接近纯 memory-bound。（见第 31 题）

### 21. 序列长度变成 64 倍，attention 矩阵变成 4096 倍，为什么实际只慢了约 10 倍？
1. T² 的部分只占一小块：大部分计算在线性层（c_attn、c_proj、MLP、lm_head），只 ∝ T。GPT-2 在 T = 1024 时注意力矩阵只占总计算量的约 13%
2. 短序列时 GPU 没吃饱（memory-bound 的平坦区），计算量增加并不会让时间同比增加

### 22. 怎么提高 decode 阶段的 GPU 利用率？
把多个请求的 decode 合并成一个 batch：读一次权重，同时服务多个 token，提高算术强度。平坦区说明一次多处理几个 token 几乎不多花时间。→ 这就是 batching / continuous batching（M2）。

### 23. 什么是 GQA？为什么现在的大模型都用它？
Grouped-Query Attention：q 有很多个头，k、v 只有少数几个头，由多个 q 头共享（如 Qwen2.5-7B：q 28 头，k/v 4 头）。

目的是**压缩 KV Cache**：缓存缩小到 1/7，decode 每步要读的数据更少，同样的显存能装下更多请求，吞吐更高。代价是表达能力略有下降。不用 GQA 的话，Qwen2.5-7B 一个 32K 请求的 KV Cache 要 12.25 GB。

### 24. 长度不同的请求怎么放进一个 batch？为什么 vLLM 不用 padding，而是把 batch 压平？
**padding：** 短的补齐到最长的长度，补出来的位置全是无效计算；请求长度差得越多，浪费越大，还要额外处理 padding 的 mask。

**压平（packed / varlen）：** 把所有请求的 token 首尾相接排成一排 `(N, C)`，用 `seq_lens` 记住每个请求占几个：
- 线性层、LayerNorm、MLP 每个 token 各算各的，直接对 `(N, C)` 算，**一次矩阵乘服务所有请求**，只算真实的 token
- attention 按 `seq_lens` 切开，每个请求和自己的 KV Cache 单独算

**项目里：** `miniserve/packed.py` 的 `packed_attention`、`packed_forward`；检查脚本验证了压平一起算和每个请求单独算的结果完全一致。

### 25. 为什么 prefill 和 decode 可以放进同一个 batch？
压平之后，线性层根本不关心 token 属于哪个请求、是 prefill 还是 decode；attention 又是按请求分开算的，每个请求用自己的缓存和自己的 mask（`(n, L)`，`diagonal=L-n`）。所以新请求送整个 prompt、老请求只送 1 个新 token，可以排在同一排里一次前向算完。

### 26. 推理引擎怎么只算最后一个 token 的 logits？为什么要这样做？
用 `seq_lens.cumsum(0) - 1` 算出每个请求最后一个 token 在第几行，先用这组下标取出这几行 `x[last]`，**再**过 `ln_f` 和 `lm_head`。

`lm_head` 是 GPT-2 里最大的矩阵（768 × 50257）；prefill 时只有最后一个 token 的 logits 用来选下一个词，其他位置的都用不上。一个 100 token 的 prompt，这样能省掉 `lm_head` 这一步 99% 的计算。

### 27. 推理引擎是怎么调度请求的？static batching 和 continuous batching 有什么区别？
引擎维护两个队列：**waiting**（已到达、还没开始）和 **running**（正在生成，每个请求有自己的 KV Cache）。每一轮 `step()`：
1. **调度**：按策略把请求从 waiting 放进 running
2. **一起前向**：running 里刚加入的请求送整个 prompt（prefill），其他请求只送上一个生成的 token（decode），压平后做一次 `packed_forward`，每个请求得到 1 个新 token
3. **收尾**：生成够了的请求移出 running，释放它的 KV Cache

两种调度策略：
- **static batching**：一批请求全部结束后，才放下一批进来。一批里只要有一个请求要生成很长，其他早就结束的请求的位置就一直空着，GPU 在为越来越少的请求干活
- **continuous batching**（iteration-level scheduling，Orca 论文提出，vLLM 等都在用）：**每一轮**都检查，running 有空位就立刻补新请求，GPU 始终接近满载

**项目里：** `miniserve/engine.py` 的 `Engine`；同样 5 个长度不同的请求、最多同时 2 个，static 要 18 轮，continuous 只要 12 轮，且每个请求的输出都和单独生成逐 token 一致（`tests/check_engine.py`）。

**GPU 实测（`benchmarks/bench_batching.py`，RTX 3060 Laptop，float32，32 个请求同时到达，prompt 16~252、max_new_tokens 29~498，共 7788 个新 token；每种跑法的结果都和逐个生成 32/32 一致）：**

| 跑法 | 轮数 | 吞吐 (tok/s) | 加速比 |
|---|---|---|---|
| 逐个 generate_cached | - | 137 | 1.00x |
| static / continuous（batch=4） | 3037 / 2002 | 192 / 219 | 1.41x / 1.60x |
| static / continuous（batch=8） | 1776 / 1148 | 224 / 244 | 1.64x / 1.79x |
| static / continuous（batch=16） | 917 / 699 | 244 / 255 | 1.78x / 1.86x |

continuous 的轮数少了 24%~37%，吞吐却只高 4%~14%，原因见第 31 题。

## 三、GPU 与性能测量

### 28. 在 GPU 上测时间要注意什么？
1. **GPU 是异步的**：CPU 把任务交给 GPU 就返回，不等它做完。计时前后都要 `torch.cuda.synchronize()`，否则测到的只是"交任务"的时间
2. **先预热**：第一次运行有初始化开销（加载计算程序、分配显存）
3. **多次取平均 / 中位数**，并记录测量条件（GPU 型号、精度、batch、序列长度）

**项目里：** `benchmarks/bench_no_cache.py`、`bench_kv_cache.py`。

### 29. 显存碎片化 / PyTorch 缓存池膨胀（项目里遇到的真实问题）
**现象：** 无缓存生成 1000 token 时，实际计算峰值只用约 0.6 GB 显存，但 PyTorch 缓存池（reserved）涨到 3.6 GB 以上，最终超过 6 GB；Windows 把数据挪到内存里，速度慢了几十倍。

**原因：** 序列每步变长，每次申请的张量都比上一次大一点。缓存池为了复用会留着释放掉的块，但旧块都比新需求小，用不上，只能不断申请新显存。

**解决：** `torch.cuda.set_per_process_memory_fraction(0.8)` 限制上限，到达上限时 PyTorch 会先释放缓存池里没在用的块，而不是溢出。

**联系：** 推理系统中 KV Cache 不断变长、大小各不相同，同样会产生碎片 → 这是 PagedAttention（M3）要解决的问题之一。

### 30. 推理服务的性能怎么衡量？吞吐和延迟有什么区别？
- **吞吐（throughput）**：单位时间生成多少 token（output tokens/s），也常看每秒完成多少个请求（requests/s）。有的工具报的是"总 token/s"（prompt 也算进去），对比别人的数字前先看清楚定义
- **延迟（latency）**：单个请求的体验
  - **TTFT**（Time To First Token，首 token 延迟）：排队 + prefill 的时间
  - **TPOT / ITL**（每个输出 token 的间隔）：主要是 decode 一轮的时间
  - 端到端延迟 ≈ TTFT + TPOT × (输出长度 − 1)
- 两者常常此消彼长：batch 越大，读一次权重服务的请求越多，吞吐越高；但每一轮要算的东西更多，单个请求的 TPOT 会变长。调度策略（比如 batch 上限）就是在两者之间取舍
- 两种测试场景：**离线**（所有请求一开始就到齐，比谁先做完，看吞吐）；**在线**（请求按一定速率陆续到达，看在满足延迟要求的前提下能扛住多大的请求速率）

**项目里：** `benchmarks/bench_batching.py` 测的是离线吞吐：32 个请求同时到达，吞吐 = 生成的新 token 总数 / 总耗时（prompt 的 token 不算）。实测：逐个跑 137 tok/s，continuous（batch=16）255 tok/s。同时 decode 一轮的时间从 batch=1 的约 8 ms 变成 batch=16 的约 62 ms（`benchmarks/bench_step.py`），也就是每个请求的 TPOT 变长了 7 倍多 —— 吞吐提高了，单个请求反而更慢，就是上面说的此消彼长（在我们的实现里尤其明显，见第 31 题）。

### 31. 为什么 continuous batching 只比逐个跑快 1.86 倍、比 static 只快 4%？（项目里的真实发现）
**现象：** 预测 batch=16 能快约 10 倍，实测只有 1.86 倍（数据见第 27 题）；continuous 的轮数比 static 少 24%，吞吐只高 4%。

**用数据拟合：** 总耗时 / 轮数 = 每轮耗时，和"每轮有几个请求"几乎是一条直线：
```
每轮耗时 ≈ 4.3 ms（整批共用）+ 3.55 ms × 这一轮的请求数
```
- 每个请求自己的 3.55 ms 省不掉，每个 token 至少 3.55 ms，而逐个跑是 7.3 ms → 加速上限约 **2.1 倍**
- continuous 少跑的轮数，只省掉了每轮固定的 4.3 ms（218 轮 × 4.3 ms ≈ 0.9 s，实测差 1.3 s）

**profiler 验证（`benchmarks/bench_step.py`，所有请求都在 decode，上下文约 128）：**

| 请求数 | 每轮墙钟 | 每轮 GPU 计算 | GPU 忙碌占比 |
|---|---|---|---|
| 1 | 8.2 ms | 2.3 ms | 29% |
| 4 | 20.4 ms | 3.6 ms | 17% |
| 16 | 62.2 ms | 8.2 ms | 13% |
| 32 | 121.2 ms | 13.8 ms | 11% |

每多一个请求，墙钟多约 3.65 ms，GPU 计算只多约 0.37 ms → **每个请求的开销 90% 在 CPU 那边**，GPU 大部分时间在等。

**根因：** `packed_attention` 对每个请求写了 for 循环，每个请求每层约 11 个小 kernel（cat、matmul、造 mask、softmax……），12 层约 130 个。每发一个 kernel，Python、PyTorch 分发、驱动提交都有固定开销（**kernel launch 开销**），和数据量几乎无关：实测 1 千个数乘 2 要 13 µs，1 百万个数也只要 30 µs。decode 时每个请求只有 1 个 token，这些 kernel 都很小，时间几乎全花在发射上。

**怎么解决：**
- 用**一个 kernel 同时算所有请求的 attention**（vLLM 的 PagedAttention、FlashAttention 的 varlen 版本），每轮的 kernel 数不再随请求数增长 → M3
- 减少发射次数：kernel 融合、**CUDA Graphs**（把一整轮的 kernel 录下来一次性提交，vLLM 的 decode 就用它）
- 理论上限：如果 CPU 开销完全消除，batch=16 每轮只剩约 8 ms 的 GPU 时间（这是估算，不是实测）

**项目里：** `benchmarks/bench_batching.py`、`benchmarks/bench_step.py`；瓶颈在 `miniserve/packed.py` 的 `packed_attention`。面试时可以按"预测 → 实测不符 → 拟合 → profiler 定位 → 针对性优化（M3）"来讲。

## 四、PyTorch

### 32. `view`、`transpose`、`contiguous` 的关系？
- `view` 只重新解释形状，不移动数据，要求内存连续
- `transpose` 只改变"读取顺序"，不移动数据，结果在内存中不连续
- 所以 transpose 之后直接 view 会报错，要先 `.contiguous()` 把数据按新顺序重新排一遍（或用 `reshape`）

### 33. 原地操作和非原地操作？
- 不带下划线的（`transpose`、`masked_fill`、`cat`……）返回**新张量**，原张量不变，必须赋值接住
- 带下划线的（`masked_fill_`、`copy_`）**原地修改**
- 别人传进来的数据不要原地改；加载权重时就是要改模型自己的参数，必须用 `copy_`

### 34. `nn.Linear` 的权重形状？加载 HF GPT-2 权重时为什么要转置？
`nn.Linear(in, out)` 存的权重是 (out, in)，计算 `x @ W.T + b`。HF GPT-2 用的 `Conv1D` 存的是 (in, out)，所以 c_attn、c_proj、c_fc、mlp.c_proj 要转置。

**陷阱：** attn.c_proj 是 768×768 的方阵，忘记转置**不会报错**，只会悄悄算错。最危险的 bug 是不报错的那种，所以每一步都要和 HF 做数值对比，而不是只看形状。

### 35. `nn.Module`、`state_dict`、`ModuleList`
- `nn.Module`：`__init__` 里定义带参数的零件，`forward` 里组装计算；`model(x)` 自动调用 forward
- `state_dict()`：参数名 → 张量的字典，参数名就是属性路径（如 `h.0.attn.c_attn.weight`），所以属性名和 HF 一致才能按名字加载
- `nn.ModuleList`：PyTorch 能"看见"里面参数的列表；用普通 list 的话，参数加载、`.to(device)` 都会漏掉

### 36. `@torch.no_grad()` 的作用？
告诉 PyTorch 只推理不训练，不记录计算图和梯度，更快、更省显存。

## 五、Paged KV Cache（M3）

### 37. PagedAttention / Paged KV Cache 是什么？解决什么问题？
把 KV Cache 切成固定大小的**块**（每块放 `block_size` 个 token 的 k、v），开工前一次性开好一个缓存池；请求按需分配块，块不必连续，用**块表**（block table）记下"请求的第 i 个块是池子里的几号块"。和操作系统的分页一一对应：块 ⇔ 物理页，块表 ⇔ 页表，请求里的第几个 token ⇔ 虚拟地址。

解决的问题：
1. **不用按最大长度预留显存**：每个请求最多浪费最后一块里没用上的位置，同样的显存能同时跑更多请求（vLLM 论文说 KV Cache 的浪费从 60%~80% 降到 4% 以下）
2. **没有碎片**：块大小统一，任何空闲块都能给任何请求用（对比第 29 题的缓存池膨胀）
3. **不用每步复制缓存**：新 token 的 k、v 直接写进块里，不像 `torch.cat` 那样每步把整个缓存复制一遍
4. **能一次算完所有请求的 attention**：所有请求的缓存在同一个池子里，靠块表就能找到，不用对每个请求写 for 循环（第 31 题的瓶颈）

**块分配器**：空闲块列表（`deque`）+ 已分配集合（`set`）。分配从空闲列表最前面取；释放时先检查块确实已分配，防止重复释放 —— 否则同一个块会被分给两个请求，k、v 互相覆盖，结果悄悄算错（和 C++ 的 double free 是同一类 bug）。

**槽位换算：** 池子按块排好槽位，请求里第 `pos` 个 token 的槽位 = `块表[pos // block_size] × block_size + pos % block_size`。一轮里所有新 token 的 k、v 用下标张量一条语句写进池子（`pool.k[layer, slots] = k`），不用 for 循环。
